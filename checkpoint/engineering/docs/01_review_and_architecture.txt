01 现有交付审查与目标架构

审查对象：三份 DOCX 与两个 ZIP，输入哈希见 evidence/input_sha256.json。保留原件；本包作补充版本。
优先级：用户本次定位 > 20261003 Baseline > 原蓝图/旧交接包；冲突需正式契约评审。

已成立的基础
1. 既有 runtime_reference 处理工具注册、角色允许清单、参数/输出 schema、轮数限制和思考内容回传。
2. capability_runtime 有版本/哈希验证和确定性规则；八项操作规程可沿用。
3. transaction_reference 有预算预留、唯一操作键、原单查询、撤销与派发竞态的 SQLite 参考实现。
4. 原始 107 项本地测试本次复跑；不能将测试数量等同上线成熟度。

需要修正的断层
P0  商业事实规范之前主要是要求说明，未形成完整执行链。
    本包新增十个本地契约定义、逐字段结构化证据绑定、费用/资格/到期门禁及完整决策快照。
    剩余：GTIN/批次、退货费用与地点、配送时段、权益叠加、真实来源审核等生产字段仍需完善。

    本包限定最终 JSON 决策、独立重算和结构化买家卡；真实模型仍待 Key 验证。
P0  旧付款授权摘要未直接覆盖全部商品/履约/权益/收款方事实。
    新桥接把完整快照哈希纳入 plan_id，再纳入既有授权指纹；变化触发新方案及新人工确认。
    剩余：生产数据库须在派发事务中读取最新受信版本并原子绑定，不能照搬内存夹具。

P1  原合同定义 28 个应用验收场景，不等于执行过 28 个应用端到端场景。

职责边界
买家/商户/运营 UI -> 可信 API 会话与字段授权 -> Agent worker（只读研究工具、生成方案）
                                                -> 业务服务（金额、资格、证据、方案版本）
人工确认 -> 可信授权端点 -> durable outbox -> transaction worker -> 单一 PSP
PSP 回调与主动原单查询 -> reconciliation -> 业务状态投影 -> 三端 UI
停止按钮直接请求可信后端；不能排在模型思考队列后。
只有交易 worker 持有支付凭证。Agent 不持 service-role、PSP 密钥、任意 SQL 或 shell 执行能力。
六类角色按任务启用；知识候选整理默认不启用。增加模型角色数量不是智能程度的指标。

部署建议（尚未部署）
三端可继续 Next.js/Vercel；Python 作为 Agent 和确定性业务服务；Supabase 用于身份、Postgres、私有证据。
长时 Python worker 应选择有 durable queue、重启恢复和可观测能力的承载环境，经故障恢复试验后确定。
如果采用 Sites，仅以前端/JS Worker 通过 HTTPS 调用 Python 服务；不能把 Python 原样部署为 Sites Worker。
Charming 可用于低风险体验原型；不要让体验原型的持久状态承担付款账本。
Sports、WordPress、Chess 与本切片无直接业务关系，不引入其额外运行依赖。
HKT/The Club 仍是候选，不能表示已合作；公开商户页面也不产生下单权限。

三端具体交接
买家：委托硬条件、两家证据卡、未知/冲突提示、版本化确认、直接停止、订单与付款分别显示。
商户：只见自己的需求/订单；结构化报价与有效期；库存/配送确认；争议材料单独保留。
运营：UNKNOWN 待办、签名验证失败/对账差异、原单查询、人工接管；退款必须单独受权和审计。
关键金额、订单号、付款状态来自业务对象；模型只能给出带依据的解释，不能覆盖这些字段。

建议新增受控接口（设计提案，非现成端点）
GET  /tasks/{id}/offers           返回两个允许来源的只读报价投影，带证据和时间戳。
POST /tasks/{id}/decision         后端重算并冻结快照；模型不能自己发布。
POST /decisions/{id}/challenge    可信会话生成一次性人工确认 challenge。
POST /mandates                   绑定 challenge、快照摘要、商户/收款方、HKD 上限、过期时间。
POST /orders/{id}/stop           直接撤销；返回停止阶段和原付款实际状态。
GET  /orders/{id}                分别返回 checkout/order/payment/fulfillment 状态。
POST /provider/callback          原始体验签、去重、金额/商户/币种匹配、版本处理。
协调既有 reference/contracts/openapi.json 的命名及版本，避免维护两套冲突 API。

交付顺序与完成定义（角色工单；时间是排期建议，不是已经完成）
E01 契约负责人：定案十个新契约和旧 Plan 的迁移，明确各环境枚举及事件映射；依赖无。
E02 商业数据：解决真实 SKU 产地冲突，取得 GTIN/费用/地址配送/退货物流证据；依赖 E01。
E03 AI 工程：配置 Key，完成 /models 与三场景各十次真模型调用，保留失败；依赖 E01。
E04 身份后端：会话到可信上下文、租户/资源授权、RLS、私有证据和短时访问；依赖 E01。
E05 支付工程：选一个支持 HKD、幂等和原单查询的 PSP，完成签名回调与沙盒故障矩阵；依赖 E01/E04。
E06 前端：三端业务卡、UNKNOWN 和停止反馈，禁止用自然语言推测付款成功；依赖 E01。
E07 平台工程：Postgres 原子预留/outbox/dispatch claim、worker 重启与双 worker 并发；依赖 E04/E05。
E08 研究/商户运营：真实三组试验、盲评、处理时长与成本；依赖 E02/E03 和稳定任务体验。
E09 独立审查：金融/身份变更由非作者复核，跑原 28 个应用场景，检查部署回滚和恢复；依赖前述工单。

生产数据库要点（待工程实现，无迁移声称）
对 tenant+plan、tenant+command_key、provider+provider_event_id 建唯一约束；命令重放校验请求摘要。
预算更新、授权检查、operation 创建及 outbox 插入处于同一数据库事务。
dispatch claim 与 revoke 同一行/同一序列化规则；检查授权版本、证据发布版本、quote TTL、payee 和 HKD。
