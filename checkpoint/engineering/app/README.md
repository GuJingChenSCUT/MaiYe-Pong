## 本次停止交互修复（stop-ui-r2）

1. 停止使用独立请求通道与状态，不等待普通确认、补答或列表刷新完成。停止按钮和本次明确确认按钮不被普通 `busy` 禁用；仍由后端事务裁决停止与派发的先后关系。
2. 每次打开弹窗清空 `returnValue`，捕获本次任务和会话。只有明确提交“送出停止要求”的按钮才发请求；Esc、取消及程序关闭只关闭弹窗。关闭时不再根据旧返回值决定交易操作。
3. 停止超时/响应丢失后重试同一幂等键；没有收到回覆时不先显示“已停止”。若后续 GET 已取得 `user_stop_requested` 事件，较晚的网络错误不能抹掉该确认。
4. 对任务版本、操作版本、会话、选中任务及列表读取序号进行检查。迟到的确认、补答、GET 或列表响应不能覆盖较新停止记录，也不能将页面切回另一任务。
5. 停止提示和结果区共用 `paymentStatus()`，优先读取 `payment_status`，兼容 `payment_state`，最后回退到 `state`。当前商户／PSP 尚未接入；这只是统一现有状态解释。
6. 页面操作计数更名为“已记录的三类操作”，明确不包含全部核对、登录、钱包确认、跳转和接管。

本次没有修改后端交易内核、数据库 Schema 或授权接口。停止仍不能保证外部付款未发生；明确批准后的停止请求要以同一操作的权威付款及订单状态判断。

**新增待关闭问题：测试数据库损坏。** 首个长期运行的工作区测试库报 `sqlite3.DatabaseError: database disk image is malformed`，研究 worker 在线程中退出，后续任务停留在规划状态。这次运行在八项检查后中断；之后独立新库完成九项检查，并修正手机端布局。新库通过不能抹去此前故障。

默认及提升权限环境均为 SQLite 3.53.1；工作区与 `/tmp` 均在带 `fsync=volatile` 的同一 overlay 上。根据 [Linux OverlayFS 文档](https://docs.kernel.org/filesystems/overlayfs.html#volatile-mount)，该宿主不适合证明断电持久性；**这不是本次损坏的已证明原因**。`/tmp` 仅用于隔离新库，不代表换到了可靠文件系统。

故障实例已停止，原库及当时可取得的旁路文件保留；交付包只含错误记录、文件摘要和检查结论，不包含会话数据库、登录码或密钥。后续需要定位损坏原因、在目标宿主核验锁/同步和重启恢复，并增加 worker 健康与不可服务状态处理。初始化数据库失败时的连接关闭也应纳入修复，但不能将资源清理改进冒充损坏根因修复。[SQLite WAL 文档](https://www.sqlite.org/wal.html)说明 WAL 属于数据库持久状态，取证及恢复不能只搬主文件而忽略旁路文件。

因此当前准确状态是：**停止交互修复及定向浏览器检查完成；停点一仍待真实 DeepSeek 验收和存储故障关闭。** 商户、钱包及提供方恢复仍保留停点二独立审阅。本轮没有触发真实付款。

证据入口为 `verification/stop_ui_revision.json`、`stop_ui_delta.json` 与 `stop_interaction/`。其中 `interrupted_browser_run.json` 和 `storage_incident.json` 保留故障，`browser_before_mobile_fix.json` 保留九项通过及手机布局失败，`mobile_browser_checks.json` 记录布局修复后的独立复查。

## 2026-10-03 本机可靠性刷新

本轮修复数据库初始 PRAGMA 失败时的连接释放；连接明确启用 WAL、FULL 同步，运行期间丢失数据库时拒绝自动创建空库。损坏或异常日志模式会隔离当前进程，不能靠一次新库检查自动解除。研究 worker 在领取、执行及保存结果失败时保留进程与退避重试，未保存的研究结果按原任务的租约和 fence 恢复；此重试机制不处理付款指令。`GET /api/v1/health` 提供不含路径或凭证的数据库与 worker 状态；`--no-worker` 明确标为 `external_unmonitored`，不证明外部 worker 存活。

存储不可用返回 `503/STORAGE_UNAVAILABLE`，不表示停止、取消或退款成功。内置 worker 不可用时，新委托、修改、重跑与审批返回 `503/WORKER_UNAVAILABLE`；若存储仍可用，用户仍可停止原任务。恢复后必须查询原任务，不能另建付款来处理未知结果。Windows 静态资源使用固定 HTML/JavaScript/CSS MIME，避免系统注册表错误映射令 `nosniff` 拒绝执行；早期拒绝请求时有界读取小请求体，避免关闭未读 POST 时丢失错误响应。

`tests/test_storage_reliability.py` 增加 14 项针对性检查，包含隔离临时库的损坏注入、连接清理、丢库、写锁、保存失败、worker 存活、停止不可假成功、24 个任务并发创建与停止、重开一致性和静态 MIME。本机刷新证据位于 `../verification/refresh_20261003/`；最终统一结果以该目录的刷新报告为准。**原事故根因仍未确定，原库和 sidecar 未随本交付包提供。以上工程防护、新库通过和 FULL 配置都不能关闭原事故，也不能证明断电后的硬件持久性。**

| 场景 | 验收重点 |
| --- | --- |
| 正常 | 实际工具调用、正确参数/任务版本、最新事实与符合用户偏好的方案；不强制最低价 |

## 现在可以操作什么

1. 启动服务并用服务端生成的买家存取码登录。
2. 点击「填入合成商品演练」。这是显式模板；任意真实商品不会被暗中换成测试肥皂。
3. 删除预算后提交，观察系统只询问预算。补答 100 港元后恢复同一个任务。
4. 选择「较早送达」，观察两家比较，推荐预算内较贵但更快的 B；选择省钱则推荐 A。
5. 核对确认卡：商品 SKU、包装量、购买量、商品小计、费用、即时优惠、现金支出、收款方及条件版本。
6. 勾选并确认，观察同一快照对应的委托及操作入队。网页没有自动派发付款功能；唯一 `PENDING` 命令由内部测试或数据库记录核对，不在页面展示完整命令状态。
7. 点击停止，观察尚未派发的操作变成 `STOPPED`；刷新或重启服务后仍可查看记录。命令转为 `CANCELLED` 通过内部测试或数据库记录核对。
8. 新建任务选择「运费上升」或「两家都无法供货」，观察改选或规则停止。商品文案要求忽略预算也不能获得权限。

商品来源、真实模型、付款环境分开显示。这里的送达时间、价格、售后与支付选项都是明确的合成测试数据，不能用于证明香港真实购物覆盖或已节省费用。

## 本机启动

需要 Python 3.12。下列命令从工程根目录执行；依赖安装和实际模型调用需要对应网络权限。

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m app.task_api --db ../local_state/hacku.sqlite --port 8765 --bootstrap
```

打开 `http://127.0.0.1:8765`。终端首次输出买家、商户 A 和运营三份本地存取码，请分别保管。角色来自服务端绑定，页面不能选择或伪造角色。商户只见本店相关商品及订单状态；运营看必要任务状态；二者不能批准或派发付款。

重启时使用同一数据库，不再加 `--bootstrap`：

```bash
python -m app.task_api --db ../local_state/hacku.sqlite --port 8765
```

此入口强制仅监听回环地址。存取码换取 HttpOnly、SameSite 会话；会话及角色绑定持久化、会话八小时到期。这是本地开发身份，尚未实现线上身份提供方、HTTPS 部署及生产运维。

如需单独运行研究 worker，两个进程必须使用**同一数据库文件**：

```bash
python -m app.task_api --db ../local_state/hacku.sqlite --port 8765 --no-worker
python -m app.agent_worker --db ../local_state/hacku.sqlite
```

两个命令分别在不同终端运行。worker 执行研究任务；付款命令不进入这个租约重试循环。

## DeepSeek 接线与当前阻塞

服务进程从环境读取 `DEEPSEEK_API_KEY`，`DEEPSEEK_MODEL` 默认为 `deepseek-flash`。不要把密钥写入网页或提交到工程。程序会查询官方模型列表并校验实际模型标识；每次调用记录请求/返回模型、使用量及时间，不输出密钥、供应商原始报错或私有推理内容。

真实入口为 `slice04.agent.run_task_v1`。先运行买家规划，再按需要运行商品事实核查；工具由 `app/task_tools.py` 的服务端 handler 执行。模型不能批准、付款或直接读数据库。补答从当前业务对象开始新一轮，旧结果必须通过任务版本、租约持有者、有效期和 fencing 检查。

目前两个角色分别限制 14 轮、20 次工具调用、每轮最多 4 个调用、输出 2048 token。一次 `run_task_v1` 的两个角色共用最多 16 次 completion、32768 输出 token 预留、单次完整请求 131072 字节和累计请求 524288 字节上限；180 秒截止时间从模型发现前开始计算。HTTP socket 超时不超过剩余时间，迟到结果拒绝使用；这不等于严格墙钟时间的网络中断保证。

研究任务最多领取 3 次，每次领取都可能使用一轮上述额度，因此这些限制不是任务整个生命周期的货币费用上限；真实调用前仍需团队核对账户能力与费用预算。工作进程崩溃可能造成一次模型调用重复计费，但不能重复建立付款。未知的提供方返回模型标识记录为 `provider_model_identity_unverified`，不能计作 DeepSeek Flash 验收；须依据实际官方返回核验对应关系。

模式含义：`live` 必须实际调用 DeepSeek；缺配置返回 `blocked`；`scripted` 是明确的固定逻辑演练；注入 transport 固定标记 `test_transport`，不能算真实模型证明。

四类在线验收入口如下。只有团队已配置并确认预算后才使用收费开关：

```bash
python tests/test_agent_live.py --live-out ../local_state/live_model_matrix.json --allow-provider-charge
```

上传基线证据中，该矩阵的正常、缺项澄清、运费变化、恶意商品文案四项均为 `blocked / DEEPSEEK_API_KEY_MISSING`；没有调用 DeepSeek。`research_success` 只代表研究完成，`task_success` 不会因选出了商品而伪装成购物成交。

本轮专业输入是服务端版本化任务、确定性规则与有字段证据的合成目录。旧知识/案例包仍按审阅状态保留；尚未新增正式知识检索或 RAG 服务，也没有将草案案例晋升成可执行商品事实。六类 Agent 仍是完整目标的逻辑分工，本轮实际启用两类。

## 接口与执行边界

接口以 `schemas/application.openapi.json` 为准；V1 领域对象见 `schemas/commerce.schema.json`。原 v0.4 工具和参考契约仍隔离保留。

| 接口 | 作用 |
| --- | --- |
| `POST /api/v1/session` | 存取码换取服务端会话和 CSRF token |
| `POST /api/v1/intents` | 保存输入与草稿，自动登记研究任务 |
| `POST /api/v1/tasks/{id}/answers` | 按两个版本号合并回答/修改条件，旧方案失效，自动恢复研究 |
| `POST /api/v1/tasks/{id}/runs` | 显式重试允许的研究阶段，不重试付款 |
| `POST /api/v1/tasks/{id}/approvals` | 绑定当前 snapshot/challenge，原子建立委托与唯一命令 |
| `POST /api/v1/tasks/{id}/stop` | 直接后端停止，不经过模型，不要求最新页面版本 |
| `GET /api/v1/tasks`、`GET /api/v1/tasks/{id}` | 同一读取快照内鉴权及角色投影，刷新不重建操作 |

除登录外，写操作需要会话、CSRF token；任务写请求还需 `Idempotency-Key`。先认证和资源授权，再查幂等结果，最后检查版本。键范围包含租户、主体及操作，请求摘要包含目标资源；同键不同资源或正文返回冲突。重放返回原响应，随后 GET 获取当前状态。

`TaskStore.transaction()` 的 `BEGIN IMMEDIATE` 与 `StageOneKernel(conn)` **实际共用连接**。任务更新、快照、授权、预算预留、命令和审计在同一事务内提交；内核不自行 commit。原通知 outbox 不被用作付款队列，新命令有独立 `PENDING / CLAIMED / CANCELLED / COMPLETED` 生命周期。

派发 claim 同事务核对最新任务/事实/报价摘要、授权、预算、SKU、数量、金额与收款方。外部价格库存仍需未来商户适配器提供固定报价或等价的提交约束；本地事务不锁住外部系统。

claim 后崩溃或付款 UNKNOWN 的恢复设计要求核实原操作；不会像模型任务一样租约到期重发付款，未知时保留预算。现有内部测试验证 LocalPSP 原操作恢复，应用尚未接入外部 PSP 查单或自动查单 worker。LocalPSP 的显式派发与恢复仅由内部测试调用。网页不提供付款、回调或退款端点。即便本地付款成功，商户订单仍是 `NOT_CREATED`，不能据此宣称成交。

用户停止记录 `user_stop / USER_STOP`；条件不满足的规则停止记录 `rule_stop / RULE_STOP`，不冒记用户撤销。停止已 claim 的操作只撤销后续权限，页面保持实际派发/UNKNOWN 状态，不宣称零扣款。

现金公式为商品小计＋必要费用－已核实即时优惠；单价×实际购买数量＝商品小计。券实例、适用订单、资格、有效期、双向叠加规则及互斥组同时验证。预计返现和积分单列来源/观察时间/资格/兑换条件，不降低现金预算。本轮未核验实际优惠权益，不使用模拟收益证明价值。

## 老师的建议怎样约束下一步

我们保留自己的判断：香港用户重复补购日用品时，核对规格、总价、配送和售后是否构成足够明显的负担？这是待真实用户验证的场景假设，尚未完成用户招募或访谈，合成肥皂任务不能替代市场证据。

下一条真实链路仍限于一个香港收货场景、两家可核实报价、一家获准商户成交、一次明确授权、一条准确命名的钱包路线。演示必须把用户最初需求与最终订单／付款回执对应起来；条件改变时展示停止或接管。付款后的订单取消、退款受理、提供方结果与用户资金可用应分别留证。

“合作商户销售、收款、履约，我们提供获准代办和统一案件入口”是建议的经营模式，尚不是已经签署的安排。商业与运营需确定主体、实际接入权限、客服负责人、退货与损失责任以及对账退款资源。平台商品数据权限不代表买家下单权限；团队收款账户不能自动成为任意平台订单的收款方。

先用相同商品、地址和约束对照人工流程与 Agent，分别记录首次及复购耗时、页面核对／填写／跳转／确认次数、错误与接管、失败恢复时间。原平台对照和真实用户数据目前都缺失；不提前设定虚构的节省比例。推荐按硬约束和明确偏好，不暗中增加佣金权重；比较范围、商业关系及未知项要可见。心理测试和吃喝住行仍属后续方向。
