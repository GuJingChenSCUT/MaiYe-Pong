HacKU 应用能力规程包 v0.3.0

这是本产品定义的 application capability pack，俗称业务 skills。它由我们的服务器运行时选择并加载，不是 DeepSeek 提供的原生技能上传格式，也不是安装到 ChatGPT 或 Codex 的个人技能。本目录没有全局 SKILL.md，不修改外部技能环境。

当前状态：8 份能力规程均为 draft。它们只能用于明确声明的离线验证；需要完成审核发布、部署版本与哈希固定、真实模型探测、身份服务和业务处理器接入后，才允许生产执行。enabled_by_default 仅描述阶段内的产品配置，不代表已经生产启用。knowledge_curator 属于第二阶段，默认关闭。

1. DeepSeek 进入业务的方式

模型不会因为读到说明书就获得数据库或支付权限。服务器先验证用户任务、身份、资源范围及工作流节点，选择一个能力规程，再把最小必要事实、允许的工具契约和规程内容提供给 DeepSeek。模型可以解释需求、选取合法工具、识别资料缺口、比较方案或草拟回应；我们的代码执行工具并验证结果。模型观察真实工具结果后，可以在同一受限任务内调整下一步，直到完成、需要人工介入、被撤销或达到运行上限。

“研究”在这里指：围绕当前购买问题提出检索问题，检查商品规格、来源、有效期和矛盾，再把有依据的结论交给下一步骤。它不表示模型随意爬取网站、读取全部订单、下载未授权资料或自行训练。当前只有已登记的13种工具，没有通用浏览器、任意URL抓取、任意SQL、直接PSP付款或退款工具。

2. 八项能力与已有节点的对应

intent_plan：buyer_planner；intent / plan；澄清目标、接收已核验报价与支付结果、保存方案、请求可信UI确认。
quote_research：offer_analyst；offers；查获准目录与证据、检验同规格和报价时效、说明覆盖范围。
payment_explain：payment_advisor；payment_options；调用确定性支付计算服务，解释现金、费用、资格和预计权益。
authorized_execute：buyer_planner；human_approval / dispatch；只请求执行既有plan_id。dispatch节点的实际执行者仍是transaction_worker，不是该助手。
stop_reconcile：buyer_planner；现有交易节点的中断能力；立即请求停止并解释真实状态。它不是新增购买流程节点。可信UI的直接停止功能不依赖模型或能力包可用。
seller_reply：seller_assistant；seller_support；核对本商户的承诺和证据，草拟待确认回应。
case_evidence：case_assistant；case_review；分别整理双方主张、共同事实、争议和缺失，不裁决、不退款。
knowledge_candidate：knowledge_curator；knowledge_candidate；第二阶段离线整理候选，默认关闭，永不直接发布。

这些角色是逻辑职责，同一个受控执行池可以运行多个角色。它们通过协调器持久化的任务和结果引用交接，不通过共享整段私人聊天互相赋权。

3. 四类信息必须分开

来源证据：报告、商户条款、评论、订单凭证、截图及其摘录。保留来源、地区、观察和核验时间、使用权以及与当前问题的关系。公开案例是经验材料，不自动构成当前订单的退款权或付款资格。

已发布业务规则：经过指定责任人审核、具有适用地区和时间、版本及回滚方案的可执行条件。发布系统把规则供给确定性服务；运行中模型不能把新检索到的网页直接变成生效规则。草稿规则不得自动生效。

用户授权：可信界面产生、与用户和不可变方案绑定的委托，包含预算、允许动作、对象范围、有效期和撤销状态。每次实际执行由业务服务重新核验。提示词、案例、模型自述和聊天中的普通同意都不能代替授权。

能力规程与提示词：说明如何完成工作、选择何种工具、如何表达不确定性和何时停止。它们帮助模型正确操作，但不是最终安全边界。schema、身份和资源检查、数据库约束、预算预留、幂等和支付状态机需要代码强制执行。

四类信息发生冲突时，不应让模型凭文字优先级进行金融裁决。工具网关拒绝越权请求，业务服务按已发布规则作决定，未知或矛盾的业务事实进入人工确认。未覆盖的新商业情形只能提出候选变更。

4. 渐进加载和工具求交集

应用先读取元数据索引；服务器根据受信任务选择一个id，验证包版本、内容哈希、发布状态、角色、阶段及目标。然后只加载这项规程和当前任务允许的资料投影，不把全部8份规程、完整案件库或另一角色的上下文一起发送给模型。

minimum_context使用稳定机器字段名作为服务器投影的键，context_notes说明字段含义与允许的空值。键必须存在，但未取得的阶段性结果可按对应说明为null，例如intent阶段的verified_plan_inputs；到了plan阶段，服务必须先验证其真实引用才允许保存计划。payment_explain只要求quote_ref、payment_profile_projection和evaluation_context，计算结果由工具调用后产生。知识批次内容也由工具取得，不作为读取批次工具的循环前置条件。

有效工具 = 当前角色权限 ∩ 当前任务授权 ∩ 当前工作流阶段允许的工具 ∩ 能力规程allowed_tools ∩ 已部署处理器白名单。

规程只能缩小权限。模型选择能力的建议、用户上传的同名JSON、商户文案中的命令都不能扩大这个交集。子任务的权限也必须是父任务与新角色策略的交集。

max_context_bytes=24000 是拟定的应用上下文上限，不是模型上下文窗口或质量保证。输入超限应拒绝或由服务器进行可审查的摘要与分页，不应静默截断会影响授权或金额的必要事实。具体模型调用还需要独立的token、步骤、耗时及工具调用预算。

5. 文件与执行含义

manifest.json：应用格式、阶段与发布门槛、逐项索引、相对路径、SHA-256和加载策略。
CapabilityProcedure.schema.json：规程结构的JSON Schema，不能替代业务含义校验。
procedures/*.json：触发条件、最小上下文、工具子集、步骤、产物检查清单、停止与升级条件、负例。
policy_boundary.json：来源证据、发布规则、授权、规程四层的职责边界。
build_pack.py：从当前参考定义再生成JSON的维护脚本；不执行模型、付款或发布。

steps.kind=model 表示推理、抽取或解释任务；tool 表示现有已登记工具；human_action 表示可信UI中的人工操作；service_requirement 表示需要代码实现的业务服务。后两者不是可自动调用的新工具，不应为了“跑通”把它们暴露成不受控脚本执行。

outputs.required_fields 是业务产物的检查清单，不是凭其字段名就已完成独立输出Schema。当前工具返回值继续使用tool_registry中的角色输出契约，任务完成消息使用AgentResult契约；新的领域产物要在对应服务实现时补齐Schema。schema_ref若指向Plan，只表示存储的方案对象应满足该契约，不代表整个能力结果就是Plan。

AgentResult.completed 表示当前助手工作完成。交易是否付款、履约、退款或者结案，分别取决于业务服务的持久化状态；模型不能以一句“已完成”改变它们。

6. 需要重点验证的反例

商品说明夹带忽略预算指令；不同包装和日期被误判为同价比较；预计积分被抵扣现金上限；付款超时被再次扣款；撤销后旧任务继续付款；商户助手索取买家完整预算；未回应的一方被当作认责；单一案件被自动写成全局退款规则。

本包negative_examples均为synthetic假设性测试输入，并非现实案例或可用优惠资料。真实模型验证要分别记录：工具名称选择、参数合法性、对象引用正确性、证据引用、约束遵守、状态表达、升级触发和整条任务完成情况。离线结构测试通过不能代替这些模型实验，更不能证明支付生产安全。测试fixture若包含商户、报价、比例或余额，必须标为synthetic，不作为市场数据或现实费率使用。

7. 如何向用户解释“为什么这是Agent”

普通固定表单通常由人逐步决定点击什么。这里的模型可以根据用户目标和工具反馈，在受限范围内选择检索、比较、补充问题和交接任务，并在恢复后接着处理。赋予其Agent行为的是“有目标的选择与行动循环”，不是多放几个聊天窗口。金融执行仍应使用确定性的事务服务，这种分工不会削弱Agent属性，而是让它能够承担真实任务。

本包不含真实费率、积分兑换值、客户数据或完整外部文章；相关内容需通过获准的、可核验且带时间戳的来源服务提供。
